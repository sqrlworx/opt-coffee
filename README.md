# forum

Office hours where anyone can be the expert. Experts announce office hours and askers submit and +1 questions until a deadline. A moderator seeds, groups, and orders the questions. The expert records video answers back to back in the order they pick: each question is played to them, they answer, and Save moves on to the following question. Then they publish them to subscribers' feeds.

Questions can be typed, spoken, or asked on camera. Typed questions are read aloud, in a voice the asker picks, and spoken ones are transcribed, so every question can be read and played back. Answer videos get transcripts and subtitles, and the expert can describe b-roll to cut away to while they talk, which is made for them, or upload their own, and it's cut in where it fits. Readers watch the published answers as one video, with a short summary underneath that lets them jump around in it. Below that, each answer has a discussion, and the expert can start a follow-up from it.

## Run it

```bash
cd forum
npm run seed      # optional: demo data (users maya, leo, sam, priya, jo; password "password123")
npm run dev       # http://localhost:3000, with the "Acting as" user switcher in the nav bar
npm start         # same, without the switcher
npm test
```

Requires Node 22.13+ (uses the built-in `node:sqlite`). The app has no required dependencies and no build step.

There's also a mobile app, for phones (see Mobile app). It has a build step, and the server serves it at `/m/` once it's built:

```bash
npm run mobile:build   # installs its dependencies and builds mobile/dist; then open http://localhost:3000/m/
npm run mobile:dev     # http://localhost:5173/m/ with hot reload; starts the server on port 3000 too (as npm run dev), unless one's already running there (FORUM_URL to change it)
```

Joining the published answers into one video needs `ffmpeg` (with `ffprobe`) on the PATH. Without it, readers get the answers one by one. Speech (spoken questions, read-aloud and transcripts) also needs [uv](https://docs.astral.sh/uv/) and `ffmpeg`. Without uv it's switched off and everything else works. On first start, uv installs the Python dependencies and the models download (a few GB in total, cached afterwards). Speech is ready once the log shows the models loading. Finishing the joined video (see Watching) also needs uv; its first join installs its own Python dependencies and downloads its models and fonts (about 2 GB). B-roll needs ffmpeg, which is all uploading it needs; having it made also needs a Gemini API key (filmed by Veo) or uv (filmed locally). Locally, the first clip installs its Python dependencies and downloads its models (about 42 GB).

Settings and API keys can also go in a `.env` file in the working directory, which the server reads on start (it's git-ignored). Variables already set in the environment win.

To use the Claude moderator, run `npm install` (it pulls in the optional `@anthropic-ai/sdk`) and set an API key.

Recording needs camera and microphone access, and browsers only allow that on `localhost` or over HTTPS. Put a deployed server behind TLS.

## How it works

**Lifecycle.** An office hour is `open` until its question deadline, or until the expert closes it early. After that it is `closed`: no new questions or votes. Once the expert publishes it becomes `published` (to readers, once its video is ready; see Watching), which is final: the answers, their order, and the videos are locked. The "answers expected" date is shown to askers but never enforced.

**Feed.** The feed is computed per request from subscriptions. There is no fan-out table.
- *Announced* items go to subscribers of the expert.
- *Published* items go to subscribers of the expert **or** of the office hour, once the answers' video is ready.
- Feed cards are teasers that link to the office hour page. You can't ask questions or read answers in the feed. Published cards show the answer count and the first three question titles.
- Asking a question automatically subscribes you to that office hour, so you see the answer.

**Anonymous questions.** When enabled, the author is stored, so the asker can still see "you (hidden)". It is never returned to anyone else, including the expert. A question asked out loud or on camera is public, so the ask form warns that the voice or face may be recognizable.

**Moderator** (`src/moderator/`):
- *Seed suggestions*: based on the expert's bio and expertise plus the topic. The expert picks which ones to post. They then appear as "Suggested by moderator" and can be +1'd.
- *Grouping*: TF-IDF clustering, with labels taken from shared terms. With Claude enabled, page loads serve the heuristic grouping right away. Claude's grouping is computed in the background and cached per question set, so pages never wait on the LLM.
- *Follow-up questions*: taken from a published office hour's discussion (see Follow-ups).
- *Suggested order*: start with the most popular group, then repeatedly pick the next group by `0.6·popularity + 0.4·relatedness` to the previous one. Within a group, most-voted first. Votes count toward popularity. So does the asker's own question, but seed questions don't get that extra point.
- The expert can take the suggested order wholesale or build their own: add, reorder, remove, answer. Only queued questions with a recorded answer are published, in queue order.
- *Summaries* of published answers, for the short transcript under the video: the question in at most a few words, then the answer's main points (at most three). The heuristic summary is extractive: a sentence from each third of the answer, the one using the answer's most frequent words. Summaries are computed per request, like grouping: with Claude, the heuristic one is served marked `pending` while Claude's is written in the background and cached, and the page checks back for it. Only the answer after the question is summarized, and a corrected transcript gets a new summary.

**Video answers.** Answers are videos the expert records live in the planner. There is no file upload. They're recorded in *sessions*: the expert clicks **Answer from here** on any queued question (or **Start answering**, which starts at question 1), and the camera stays on while they work down the answer order. Each question's audio (the asker's recording, or the typed text read aloud) is played to the expert and mixed into the recording. It's downloaded and decoded before that question's take starts recording (the next question's while the current one is answered), so the clip starts with the question, not a pause while it loads. When it ends, they answer. **Save** keeps that take and plays the following question; on the last question it ends the session. **Skip** leaves the question's answer as it was and moves on. **Start over** replays the question and discards the take. **Exit** ends the session: if they've started answering, recording pauses and they choose **Save** or **Discard** for that answer (or **Keep recording**); while the question is still playing there's nothing to keep, so it exits right away. Esc does the same as Exit. On the last question there's no Skip, since that's the same as exiting without saving. A question asked on camera also plays the asker's video, muted, as a small picture-in-picture over the camera preview while its sound plays. It loads ahead with the sound and goes away when the question ends. It isn't recorded: readers see it over the joined video instead (see Watching). A question without audio yet is shown on screen for the expert to read out. Starting on a question that already has an answer asks first; an answered question coming up later in the session is flagged, and answering it again replaces the old answer. Each question is its own take: the browser starts a new `MediaRecorder` on the same camera stream when the expert moves on, so takes need no server-side splitting, and each one uploads in the background while the session continues. Once saved, a take keeps playing from the browser's copy for as long as the expert stays on the page, so the player doesn't reload by downloading the video it already has. The take for a question is its answer, the question followed by the response, and that clip is what readers see on the Q&A page. `PUT /api/questions/:id/video?answerStart=<seconds>` records where the answer starts within the take, and the written transcript on the public page leaves out the question part before that point. The browser records MP4 where supported (Chrome, Safari), otherwise WebM (Firefox). Takes are capped at 10 minutes. The expert can **Remove** an answer. If saving fails, the take stays in the browser with **Try again** / **Discard**, and publishing waits until every take is saved. Each take is sent as the raw request body and saved in `FORUM_MEDIA` under a random name. Videos are served from `/media/<name>` with Range support, so seeking works. Players seek a millisecond in once the metadata loads, so browsers show the first frame instead of a blank player. Draft videos are visible only to the expert; published ones are public. Files that no draft or published answer uses any more are deleted when a take is replaced or removed. On publish, recordings for questions that weren't published are deleted too. Experts should wear headphones: the question is mixed in digitally, so a mic that also hears it from the speakers records it twice.

**Watching.** Readers watch the published answers as one video. On publish, `src/video.js` joins the takes end to end in the published order, in the background with ffmpeg. Each take is re-encoded to 1280×720, 30 fps H.264/AAC first, with its b-roll cut in (see B-roll). Takes can be MP4 or WebM, from different cameras, and the browser's recordings have no reliable durations. The parts are then joined without re-encoding again into an MP4 that streams before it has fully downloaded. The office hour stores the file and where each answer starts and ends in it (`video_chapters`), and how far into each answer its question's sound starts. A take records the question a little late (about 50 ms, the browser's audio latency) and joining shifts it a little more, so the server finds each question's audio in the joined video by lining up how loud each is over time, to 5 ms. Videos joined before that are searched on startup. This takes a few minutes for a long office hour. Until it's done, readers see the office hour as it was when questions closed: the API reports it as `closed`, with no answers, and it isn't in feeds or Explore's "Recently answered" yet. The expert sees it as published, with a note that the video is being processed. Their page polls `GET /api/office-hours/:id/video` and shows the video as soon as it's ready. If joining fails, or without ffmpeg, the page shows each answer's own video instead. On startup, the server picks up pending joins and joins office hours published before this existed. The joined video is public, like the answers.
- *Finishing* (`src/finish/`, run with uv) makes the joined video look and sound like a studio podcast clip, without changing its timing. Each take is rendered at 1920×1080 instead of just re-encoded, in pieces of a few seconds in parallel. It takes about as long as the video on a few cores, longer on fewer; the 3-minute sample took about 3 minutes on a large server.
  - *Picture:* the person is cut out with [Robust Video Matting](https://github.com/PeterL1n/RobustVideoMatting) and lit like a portrait. The side of the face that's already lit gets more light, falling off down the body, and gains a little local contrast. The room behind is darkened by a little under two stops, cooled, desaturated and thrown out of focus. Then come a filmic curve, a vignette and a light teal/warm split tone, a careful upscale with sharpening, and a fine grain. White balance, exposure and the room's level are measured once per take from the face ([YuNet](https://github.com/opencv/opencv_zoo/tree/main/models/face_detection_yunet)) and the matte, and the face's position is smoothed, so nothing flickers. A take of another shape sits over a blurred copy of itself.
  - *Sound:* by default (`studio`) the voice is restored with [Sidon](https://github.com/sarulab-speech/Sidon), a speech-restoration model that resynthesises it as clean, full-band studio speech. The room and noise go, and the chest of the voice and the top end a headset never picked up come back. The words and the speaker stay, though the voice's colour changes a little, much as between two microphones. With `natural`, [DeepFilterNet3](https://github.com/Rikorose/DeepFilterNet) only removes the room and the recorded voice is kept. If Sidon can't run, the voice falls back to that. Either way, the voice is then matched to the standard speech spectrum (ANSI S3.5), with a broadcast microphone's proximity warmth, presence and a little air on top. Headset and laptop microphones sound boxy and dull, and Sidon comes out warm; boosts are capped, and bands the microphone never picked up are left alone. An expander keeps the pauses quiet, and a slow leveller and a fast compressor follow. The question (the asker's recording or the read-aloud text) and the answer are each matched and levelled to −16 LUFS, with peaks under −1.5 dBTP.
  - *Captions* are burned in when the answer has a transcript, so joining waits for transcripts still being made. They show a few words at a time, low in the frame, with no box behind them: white for the expert, yellow italics for the question, which is captioned as it was asked (see Answer videos below). Louder words are set bigger. A phrase's key word is set heavier (a number, a name, or a word said louder or drawn out), and a stressed little word (*not*, *never*, *really*) in italics. Words are timed from speech-to-text, kept with the transcript, and spread over a line the expert corrected. A correction after publishing remakes the video in the background, and readers keep the current one until the new one is ready. The player doesn't draw its own captions over those answers. Captions move to the top of the frame for a take where the speaker's mouth would be behind them.
  - *The mobile app's copy.* The same pass also writes a copy of each take for the mobile app (`office_hours.video_mobile`, `mobileSrc` in the API): the same finished picture and sound, but upright, each take filling it, cropped, so that the phone can fill its upright player with it, or either half of its split screen (see Mobile app). It's 1080×1920 (9:16) when every take is that shape, as the app recorded answers before they were 3:4, so they fill the whole player uncropped, and 1080×1440 (3:4) otherwise. Split-screen b-roll isn't cut into it, since the phone plays that clip in the bottom half and crops the expert from this copy into the top half. Full-screen b-roll is, filling it like the take, under the captions, so the phone doesn't split for it. The expert has the top half whenever the phone splits, cropped to frame their face: the finisher takes the face it tracks through the take ([YuNet](https://github.com/opencv/opencv_zoo/tree/main/models/face_detection_yunet)), keeps the chin in, then the top of the head if there's room, with the eyes about a third of the way down if there's room for that (`half_focus` in `src/finish/captions.py`). Without a face, more is cropped off the top than the bottom. Its captions, the question's and the answer's, go at the bottom of that crop, under the expert and just above the split, which is low on the whole player too; they're sized by as much of the copy's width as the whole player shows, and no line is wider than a tall phone shows in fullscreen. The finisher also finds the asker's face in a question asked on camera, so the bottom half can frame them the same way, and the chapters say where both crops go (`expertFocus`, `askerFocus` in the API). It costs a second encode of each take, not a second finish, and as much storage again. Takes joined as recorded get a copy too, 720 wide, without captions. On startup, videos joined before the copy was upright, or before there were copies, or with captions burned in before they went under the expert, are joined again; until then the app plays what there is.
  - *B-roll* is cut in over the finished picture, after the grade and before the grain and captions, so the captions stay full size over it. `src/video.js` gives the finisher the ffmpeg filter that does it, the same one it uses to join takes as recorded. For split screen, the finisher fills the left half with the take, cropped to frame the expert's face while the b-roll plays (`side_focus` in `src/finish/captions.py`): centred on it across, since the page records 16:9 and the half shows only the middle half of that, and framed down as the phone's halves are. Without a face, and in takes joined as recorded, the half crops the middle across and more off the top than the bottom. Full-screen b-roll is cut into the phone's copy too. The captions stay where they are, across both halves of a split.
  - If finishing fails, the takes are joined as recorded, and the player draws the captions as before.
- *The player* has its own controls, so the captions and the asker stay on in fullscreen. It has play, a timeline with a tick where each answer starts, captions on/off (hidden when every answer's captions are in the picture), mute and fullscreen. Keys: Space/K play, ←/→ 5 seconds, F fullscreen, C captions, M mute. The controls fade while it plays until the pointer moves.
- *Captions* are drawn at the bottom from the answers' transcripts, each shifted by where its answer starts, and drop lower while the controls are hidden. They come up while the question plays too, in italics, captioned as it was asked.
- *The asker* shows at the top left while a question is being played (the start of each take, up to its `answerStart`): a picture in a white frame, with who asked underneath ("Maya asks", "Someone asks" for anonymous questions, "Suggested question" for moderator seeds).
- *The picture* is the asker's video for a question asked on camera. It's muted (the question's sound is already in the take) and kept in step with the question: it plays and pauses with the player, and seeks with it once it drifts by more than 0.3 seconds. Each one starts loading while the answer before it plays. For any other question, and until the video has a frame of that moment to show, it's a fox saying the question. It's drawn on a canvas from `public/fox.webp`, the fox with its eyes and mouth painted out, which are drawn over it so it can blink and talk. Its mouth follows the question's lip sync (see Speech), loaded while the answer before it plays, frame by frame at the player's time from where the question's sound starts in the video, so it pauses and seeks with the player and never drifts. The asker's video is timed from there too. It blinks every few seconds, sways gently, and rises a little on the louder parts. Until the lip sync has loaded, or if there's none, its mouth opens with how loud the question is (the video's sound goes through a Web Audio analyser, set up on the first click on play).
- *The summary* under the video lists each question in short, with who asked it, and its answer's main points. Each question and answer is one thing to click: clicking anywhere on it plays it from the start of its take, where the question is. The one being played is highlighted. Answers still being transcribed are summarized when their transcript is ready.
- *The discussion* is below: each question, its answer's transcript (the expert can still correct it there; the captions and summary follow), then what people said about it (see Discussion).

**Discussion.** Under each published answer, once readers can see it (the video is ready), people discuss it in text. Anyone logged in can reply to the answer, and that's as deep as it goes for them. The expert can respond to any one reply, under it. They can also add to their answer: the box for that, and what they've added, come right under the answer, before people's replies, so neither gets lost below a long discussion. What the expert writes is marked "Expert". The text boxes stay out of the way until needed: **Reply**, **Add to your answer** and **Respond** each open one, which closes again once sent. Replies and responses are shown oldest first, and can be liked (once each, not your own). `POST /api/questions/:id/replies` with `body`, plus `parentId` for the expert responding to a reply; `POST`/`DELETE /api/replies/:id/like`. The office hour's `answers` carry each one's `discussion`.

**Follow-ups.** On a published office hour, the expert can **Create follow-up Q&A**. It's the usual form to announce office hours, filled in from the one being followed up: "Follow-up: <title>", its topic and anonymity setting, and its description after a line saying what it follows up. Under it are questions the moderator took from the discussion (`GET /api/office-hours/:id/follow-up`). The heuristic picks the questions people asked in their replies, the ones the expert didn't respond to first, then the most liked, leaving out near-repeats and the expert's own replies. Claude, when enabled, writes them from the whole discussion instead. The expert ticks and rewords them, and the ticked ones start the new office hour as seed questions ("Suggested by moderator"), sent with it as `followUpOf` and `questions`. The two office hours link to each other ("Follows up on", "Followed up in").

**Speech** (`src/speech/`). Speech runs locally: faster-whisper for speech-to-text and Kokoro for text-to-speech, in `worker.py`. The server starts two long-lived worker processes with uv, so models load once. One worker serves askers waiting on a transcript; the other does background work, so a long answer video never holds up an asker.
- *Spoken questions.* The asker records up to 90 seconds in the browser, sound only (**Speak**) or on camera (**Video**). When they stop, the recording goes to `POST /api/office-hours/:id/recordings` and is transcribed while they wait (a couple of seconds). Nothing is asked yet: the asker listens back, checks the transcript and corrects anything misheard, then asks. That's `POST /api/office-hours/:id/questions` with the `recording` and the checked transcript lines, which become the question's text, so grouping, ordering and the feed treat it like a typed question. A video goes to the same endpoint (MP4 or WebM, as the browser records it). Its sound is taken out into an M4A with ffmpeg, and from there it's handled like a spoken question: that sound is what's transcribed, played to the expert and mixed into their take, and the recording the asker sends to ask is known by. The video goes along with it (`questions.asker_video`, `askerVideo` in the API) and is public like the question's audio. A video without sound is refused. Unasked recordings are private to the asker, deleted (video too) when they re-record or discard, and cleaned up after a day. If nothing intelligible was said, or transcription fails, the recording isn't kept; the asker still has it in the browser and can try again. Anonymous questions hide the name, but the recording is public and the voice may be recognizable; the ask form says so.
- *Typed questions,* including moderator seeds, are read aloud in the background. They show "Preparing audio…" until it's done.
- *Voices.* The asker picks the voice their typed question is read aloud in, from five Kokoro voices (`src/speech/voices.js`): Heart, Bella and Michael (American), Emma and George (British). Each has a ▶ button that plays a short sample of it, served at `/media/voices/<id>.m4a` to anyone. The samples are made when the server starts, on the worker that serves askers (one asked for before that is made while the asker waits), and kept in `FORUM_MEDIA/voices/`. The voice is sent as `voice` with the question and saved on it (`questions.voice`), and becomes the asker's voice (`users.voice`), picked for them the next time they ask. A question sent without one is read in the asker's voice. `GET /api/me` lists the `voices` and the viewer's `voice`. Moderator seeds, and askers who haven't picked one yet, get `FORUM_VOICE`. Spoken questions and questions asked on camera are heard in the asker's own voice, so they have no voice to pick. Each language has its own Kokoro pipeline for its pronunciation, and the pipelines share one model.
- *Lip sync* (`lipsync.py`), so the fox can say a question in the joined video: the mouth's pose 30 times a second (how open, how wide, and how much is being said), kept in `questions.lip_sync` and served at `GET /api/questions/:id/lip-sync`, as public as the question's audio. A typed question gets its lip sync as it's read aloud: Kokoro predicts how long it says every phoneme, so the mouth follows exact timings. A spoken question's is made in the background once it's asked, from its words as Whisper timed them (kept with the recording's transcript) and their phonemes from Kokoro's G2P, spread over each word. Each phoneme becomes a mouth shape that blends into its neighbours, the shapes lead the sound by 40 ms as in hand-drawn animation, the loudness shuts the mouth in silence and opens it wider on loud syllables, and every m, b and p shuts the lips for at least a frame.
- *Answer videos* are transcribed in the background after each take. A transcript belongs to its video file (the `transcripts` table), so the draft and the published answer share one. Drafts' transcripts are as private as the drafts. An answer can be published before its transcript is ready; it shows up when done. A take recorded in a session starts with the question being played. That part isn't the answer's transcript: the transcript, its text and its corrections cover what's said after `answerStart`, and the question is captioned as it was asked instead, from the asker's corrected transcript for a spoken question, or the typed text spread evenly over the time it's read aloud. The answer's captions (`/media/<file>.vtt`, and those burned in) are the two together.
- *Captions.* Word timings from Whisper become subtitle cues: at most two lines and six seconds, ending early at sentence ends and pauses. Cues are served as WebVTT at `/media/<file>.vtt`, with the same access rules as the recording. When answers are shown one by one, each video loads them as a subtitle track (use the player's CC button); the joined video draws them itself (see Watching). Transcripts are shown under answers, and a spoken question's text is its transcript. Both highlight the cue being spoken, clicking a cue plays from there, and each has a "Download captions (.vtt)" link.
- *Correcting transcripts.* Speech-to-text makes mistakes, so transcripts are corrected line by line. Each line is one subtitle and keeps its timing, which keeps the subtitles in sync; clearing a line removes it. Askers correct a spoken question before asking it (above); once asked, it doesn't change. The expert can correct an answer's transcript in the planner, and also after publishing, on the public page (`PUT /api/questions/:id/answer-transcript`). Publishing locks the answer, not typos in its transcript, which may only have finished after publishing. Corrected transcripts are marked "edited", and their captions URL changes so browsers don't keep showing the old subtitles.
- *Progress lives in the database,* so on startup the server resumes pending work. It also catches up on anything recorded before speech existed, or while it was off, and on lip sync for questions asked before it existed (a spoken one's recording is transcribed again for its word timings). The page polls `GET /api/questions/:id` while something is pending. Failures show as "couldn't be transcribed"; nothing retries them automatically, except lip sync, which is tried again at the next startup.

**B-roll** (`src/broll/`). Under each recorded answer in the planner, the expert can describe a shot to cut away to while they talk ("Close-up of hands chopping onions on a wooden board"), or an idea to show ("when eventual consistency is dangerous"). **Make b-roll** sends it (`POST /api/questions/:id/broll` with `prompt`), and a clip of it is made in the background, one at a time: filmed by [Veo](https://ai.google.dev/gemini-api/docs/video) with a Gemini API key, and otherwise on the server's CPU (below). Or they upload a video of their own (below). The planner names the model that films it (`brollModel` in `GET /api/me`): Veo's, or LTX-Video 2B.
- *Writing up the shot.* A video model can't work out an idea by itself: given "show when eventual consistency is dangerous", it makes a generic scene (a park, say). So the description is first written up, following `shot.md`, as exactly what's on screen: by GPT with an OpenAI key, else by Gemini with a Gemini key, else locally by [Qwen3 8B](https://huggingface.co/Qwen/Qwen3-8B), without its thinking. If GPT or Gemini fails, the next one down does it. It makes what the expert asked for, never something else: a diagram stays a diagram (the standard one, like the CAP theorem's triangle, if there is one), with its shapes, labels, colours and motion spelled out, and footage stays footage, with its people, action, setting, light and camera. The question and what the expert says in the answer (its transcript, which it waits for) get the details right. Only an idea with no kind of clip asked for is up to the writer: an animated diagram for a technical concept, or a live scene from the expert's example for something people do. Labels are kept to a few short words, quoted exactly, since more come out misspelled. The planner shows what was filmed. If writing it up fails, the description is filmed as it is.
- *Filming it with Veo* (`src/broll/gemini.js`), with a Gemini API key: Veo 3.1 (Fast, unless `FORUM_VEO_MODEL` says otherwise) films the shot at 1280×720 and 24 fps, 4, 6 or 8 seconds long (the shortest that's long enough), in about a minute. Clips can then be up to 8 seconds. Its sound isn't used. If Veo can't film it (out of quota, the prompt filtered, down), it's filmed locally instead, when uv is there.
- *With an OpenAI key* (`src/broll/openai.js`), GPT also describes the clip's first frame as a still image. When the clip is filmed locally, gpt-image draws it (3:2, medium quality, cropped to 16:9), and the clip starts from that picture, which LTX-Video animates: the content and composition come out much closer to what was asked than from a description alone, though the local model animates diagrams poorly. That takes about 30 seconds, and a few cents per clip. If it fails, the shot is written up and filmed locally, without a first frame.
- *Filming it locally,* with `broll.py`, run with uv: [LTX-Video](https://github.com/Lightricks/LTX-Video) (2B, distilled, with Lightricks' open weights) makes the shot at 1024×576 and 24 fps, without sound, at most 5 seconds. Writing it up locally takes about 20 seconds and filming it about 4 minutes on a large server's CPU, much longer on a small one. Each clip is made in its own process, so the models' memory is given back between them. (OpenAI's video models, Sora 2, were shut down in September 2026.)
- *Uploading a video.* **Upload a video** sends one the expert picked instead, with what they typed in the box as what it shows, if anything, and full screen if they ticked **Full screen** first (`PUT /api/questions/:id/broll/video?name=<its file name>&description=<what it shows>&full=1`, the file as the raw body; see How it looks). It only needs ffmpeg, so it works without a Gemini key or uv; without either, it's the only way. Anything ffmpeg reads will do, up to 500 MB, like a phone's MOV. The planner shows how much has been sent, and it can be cancelled until it all has. The server then makes it into a clip like the ones that are made, in a few seconds: an H.264 MP4 that every browser plays, upright, at most 1080p and 30 fps, in ordinary range (HDR, which phones film by default, is tone mapped, so it isn't washed out), and without its sound or metadata (a phone's says where it was filmed). Only as much of its start as the answer has room for is kept, and the expert is told when that isn't all of it. The file as uploaded isn't kept. Something that isn't a video, or a clip under 1.5 seconds, is refused, and nothing is kept.
- *Shorter than the answer.* A clip is as long as the answer has room for: at most 60% of the answer (from `answerStart` to the end of the take), and at most 8 seconds from Veo, 5 made locally. An uploaded one can have all of the 60%. An answer with room for less than 1.5 seconds is refused as too short.
- *Where it goes.* Once the clip is made, the moderator places it, after waiting for the take's transcript. An uploaded clip is placed right away, not after any clips being made, which take minutes each. The expert is seen first and last: the cut starts at least a little after the answer does (up to 2.5 seconds) and ends a little before it does (up to 1.5 seconds). Within that, the heuristic cuts away as the expert starts talking about what the b-roll shows, by the words it's described with: words said during it count, less the later they come, and words said just before it nearly as much. It cuts on a phrase starting (after a pause or punctuation), a sentence better still. An uploaded clip goes by what the expert said it shows or, if they didn't say, its file's name ("chopping-onions.mov"), which often does. With nothing said that matches, it goes about a third of the way into the answer, at a sentence if there is one there. Claude, when enabled, picks the moment from the answer's transcript instead, kept within the same limits.
- *How it looks.* B-roll is split screen, or full screen for a video the expert uploads with **Full screen** ticked. On the page, split screen puts the expert on the left half and the b-roll on the right, each cropped to fill its half, and the two fade in together over the expert's whole picture, and back out, over 0.3 seconds. Full screen fills the frame with the b-roll, and the expert's picture moves to the top left, framed like the asker's in the player: a 4:3 crop with rounded corners, a thin white frame and a soft shadow, fading in and out the same way. On the phone, split screen puts the expert on top and the b-roll below, and full screen gives the b-roll the whole player, with the expert only heard (see Mobile app). The expert's sound carries on throughout. In the planner the answer's video previews it, with its own controls (play, the time, and a timeline marking where the b-roll is in amber), since the video's own would be covered, or shrink into the corner; it says where it was cut in, and if it's full screen. The joined video has it cut in (see Watching), under the captions.
- *Changing it.* Asking again or uploading (**Change**) replaces it, **Remove** removes it, and either stops a clip still being made. To switch an uploaded video between split screen and full screen, **Change** opens the form with the box as it was, and it's uploaded again; b-roll that's made, or uploaded without the box, is split screen. The mobile app switches it where it is instead (`PATCH /api/questions/:id/broll` with `full`), and the clip is placed again, since where it fits depends on how it looks. Re-recording the answer places the same clip again in the new take, without making it again; removing the answer keeps it, unplaced, for the next take. A take too short for it leaves it out, with a note. A clip that couldn't be made shows as failed, with the description kept to try again. Publishing waits until no answer's b-roll is still being made, and b-roll goes with an answer only if it's made and placed. Like the answers, b-roll is the expert's alone until published, then public, and final. Clips nothing points to any more are deleted, including those left out at publishing.
- *Progress lives in the database* (`questions.broll_status`), so on startup the server makes and places any b-roll that was pending. An uploaded clip that has gone missing can't be made again, so it's marked failed.

**Drafts and publishing.** Before publishing, the planner edits a private working copy (`plan_position`, `answer_video`). The answer order saves itself whenever it changes, so leaving or refreshing the planner doesn't lose it. Publishing copies it once into a snapshot (`published_position`, `published_answer_video`), and the public page and feed read only that snapshot. Questions that weren't answered are left off the public page for everyone but the expert, who sees them folded away under the answers. Once readers can see it's published, the API doesn't send those questions to anyone else, and only counts the answered ones for them (`questionCount`, on the page and on cards). Publishing is one-way. Afterwards the planner redirects to the public page, and the API refuses edits with 409: plan saves, recording or removing videos, and publishing again. An upload that is still in flight when the expert publishes is also rejected, and its file is discarded.

**Mobile app** (`mobile/`). The same forum for phones, as a [React Native Web](https://necolas.github.io/react-native-web/) app built with Vite, over the same API and media: the server serves its build at `/m/`, so it shares the page's login, and links work in both with `/m/` in front (`/m/#/oh/3`). It does everything the page does, laid out for a phone held upright. Pages are one column; tabs along the bottom (Feed, Explore, Host, You) replace the nav bar, and make way for the keyboard. Everything tappable is at least 44 points, text fields use 16px text so iPhones don't zoom into them, and it keeps clear of the notch and home indicator. The expert's card under their name opens as a sheet when it's tapped, instead of on hover. Play buttons on questions always show, since there's no hover. The planner's two lists are two tabs: questions are added to the answer order with a tap, and moved by dragging the grip that leads the buttons at the bottom of their card (or with the arrow keys on it). While one is held every card folds to its question, so a card can go a long way without carrying answer videos past the others; the held card follows the finger, the others slide out of its way, and the page scrolls while it's near the top or bottom. Letting go unfolds them in the new order. Sliding a card left shows **Remove** behind it, which takes it out of the answer order; tapping the card, pressing anywhere else or scrolling closes it again. Recording asks for the front camera, and the recording session is full screen with its buttons at the bottom. B-roll uploads come from the camera roll. The b-roll panel starts with **Make b-roll** and **Upload a video**: the box to describe a shot opens with Make b-roll, and a video is uploaded without one, so it's placed by its file's name. Once an uploaded video is in, a **Full screen** switch shows under it.
- *Recorded for the split screen.* Answers are recorded 3:4, the shape of a phone's camera, so that each can fill the whole upright player (9:16) or either half of it (9:8) with a little cropped off either way: the whole player shows 75% of its width, and a half two-thirds of its height. A question asked on camera is only ever shown in the top half, so it's recorded in that shape, 9:8. Chrome crops these out of a webcam that's wider than tall (a 1080p webcam records 810×1080 and 1215×1080); a browser that can't records the camera as it is, and it's cropped where it's shown. They're asked for 1080 tall: asking for more makes Chrome read a 4K webcam at 4K, and MediaRecorder then records the crop at that size. The recording session's frame is the player's shape, filled as the player fills it, so the expert sees themselves as readers will, and the asker records in a frame the top half's shape. Elsewhere, players show each video in its own shape, an upright one at most 60% of the screen tall. The page's joined video stays 16:9, so an upright take sits in the middle of it, over a blurred copy of itself once it's finished (see Watching); the phone has an upright copy of its own. On the page, an asker's upright video is shown whole rather than cropped to 16:9 or 4:3, and so is an upright take in the corner while its full-screen b-roll plays.
- *Split screen instead of picture in picture.* Wherever the page shows one picture over another, or beside it, the phone splits the player in two: the expert in the top half, and the asker or the b-roll in the bottom half, each at full width (`mobile/src/media/split.js`). Full-screen b-roll doesn't split: it has the whole player. The player is upright, 9:16, and at most 78% of the screen tall, so each half is 9:8 and a split never changes its size. Between splits the main picture has the whole player. Each picture fills its place, cropped, rather than fitting inside it with bars; a half crops a person to frame their face where the server found it (see Watching), and otherwise crops more off the top than the bottom, keeping chins in. Each half slides and fades in over 0.3 seconds, like the cut to b-roll.
  - In the joined video, while a question plays, the joined video is in the top half and the asker (their video, or the fox saying it) in the bottom half. The fox stands on the bottom edge of its half, as big as fits, on its picture's own background. While an answer's split-screen b-roll plays, the joined video is in the top half too, the mobile app's copy having no split-screen b-roll cut in, and the b-roll clip plays in the bottom half in step with it (muted, since the expert's sound carries on). Burned-in captions come out at the bottom of the expert's half, just above the split (see Watching). Full-screen b-roll is cut into the copy, so the joined video keeps the whole player, the captions low on it. In a video joined before the copy was upright, the server drew the expert into the corner of the picture, so the player crops them from where `cutawayFilter` in `src/video.js` puts them. In one joined before there were copies, the captions are under the clip, so the player draws that answer's captions itself.
  - The captions the player draws (for answers without burned-in captions) sit just above the split too, under the expert. The asker's name goes at the bottom left of their half, rising clear of the controls while they show: just the name, "Anonymous" for an anonymous question, or "Suggested question" for a moderator's seed. While the joined video plays alone, they're low on it, where the mobile app's copy has its own. Over a split, they rise clear of the play button while it shows. Sideways, they're at the bottom of the left half during a split, and at the bottom of the player otherwise.
  - An answer's own video with b-roll, in the planner, or published answers that weren't joined: the take has the whole player, and moves to the top half while the b-roll plays in the bottom half. Full-screen b-roll fades in over the whole player instead, the take playing on under it for its sound.
  - While recording, a question asked on camera moves the camera to the top half and plays the asker's video in the bottom half. The rest of the time the camera has the whole frame. No faces have been found yet then, so both crop more off the top than the bottom.
  - Fullscreen on a phone turned sideways, the halves go side by side, the top one on the left. A picture alone there is shown whole, with bars: filling a screen that wide, an upright one would be cut down to a band across the face.
- The player has its own controls: a tap shows them, and they fade while it plays. The timeline is above the buttons and can be dragged with a finger, and it says which question is under it.
- The fox is drawn by `public/fox.js`, which the page uses too.

## Layout

```
server.js               entry point
src/app.js              HTTP routes (JSON API, video upload/streaming, static files)
src/db.js               SQLite schema
src/auth.js             scrypt passwords, cookie sessions
src/moderator/          heuristic.js · claude.js · index.js (facade, fallback, caching)
src/speech/             worker.py (Whisper + Kokoro) · index.js (worker processes) · jobs.js (background queue) · captions.js (cues, WebVTT) · lipsync.py (how the mouth moves) · voices.js (the voices askers pick from)
src/broll/              broll.py (writing up the shot with Qwen3, filming it with LTX-Video; run with uv) · shot.md (how a shot is written up) · gemini.js (Veo filming it, and Gemini writing it up, with a key) · openai.js (GPT and gpt-image planning the shot instead, with a key) · index.js (running it, getting uploaded videos ready, how long a recording is) · jobs.js (making b-roll and placing it, in the background)
src/video.js            joining published answers into one video with ffmpeg, cutting in their b-roll, finding each question in it, and its background queue
src/finish/             finishing the joined video: finish.py (entry, run with uv) · look.py (picture) · sound.py (dialogue) · captions.py · assets.py (models and fonts) · index.js
public/                 vanilla-JS single-page app (hash routing), and fox.webp and fox.js, the fox the players draw
mobile/                 the mobile app (React Native Web, built with Vite; served at /m/): src/pages · src/officehour · src/manage (planner, recording session) · src/media (players, split screen, transcripts) · test/
scripts/seed.js         demo data
test/                   node:test — serving the mobile app, moderator unit tests, API lifecycle tests, speech tests (with a fake engine, and lip sync with uv if installed), video tests (fake joiners, plus real ffmpeg if installed), finishing tests (caption and sound decisions, with uv if installed), b-roll tests (with a fake generator; making a real clip takes minutes, so it isn't run, but getting an uploaded one ready with ffmpeg is, if installed)
```

## Not built yet

- Notifications beyond the feed (email/push when an office hour is published)
- Editing or deleting questions; editing office hour details or deadlines after announcing
- Editing or deleting replies in a discussion, and notifications when someone replies or the expert responds
- Moderation/reporting, rate limiting, pagination
- Expert moving questions between moderator groups by hand
- Transcoding answers one by one: the joined video is H.264 MP4, but until it's ready (or without ffmpeg) a take recorded as WebM in Firefox won't play in older Safari
- Retrying a failed join (restarting the server only resumes pending ones), or a download link for the joined video
- Retrying failed speech jobs (other than restarting the server, which only retries pending ones), or typing a transcript for a recording that couldn't be transcribed
- A vertical (9:16) cut of the finished video for sharing as a short
- More than one b-roll per answer, moving it by hand, b-roll with its own sound, picking which part of an uploaded video is used (it's the start), or making it from an image the expert uploads
- Full screen for b-roll that's made, or, on the page, switching an uploaded video between split screen and full screen without uploading it again (the mobile app can)
- A GPU for finishing and local b-roll: they run on the CPU, so a long office hour on a small server takes a while to be ready, and b-roll made without Veo even more so
- Hosted speech APIs, or a GPU. Speech runs on the server's CPU: a 2-minute answer takes about a minute to transcribe with `small.en`
